# AGENT.md

## Project Overview

Daytona is a Windows NT 4.0 style desktop shell for Linux.

It is a **shell**, not a compositor and not a toolkit. It provides the desktop experience on top of an existing Wayland compositor:

* Taskbar (bottom by default, movable when unlocked)
* Start button and Start menu
* Taskbar window buttons
* Notification area and clock
* Notification balloons (Windows 2000 style)
* Desktop background, desktop icons and desktop context menus
* Run and Shut Down dialogs
* Window switching UI where the compositor does not already provide it
* A Win95-style Qt widget style
* A Windows `.theme` (Plus! 95 era) converter

Window management, window decorations, input and output handling are delegated to the compositor (labwc). Where the compositor's behaviour differs from NT, the preferred fix is a configuration change or an upstream contribution to the compositor, not a replacement compositor.

The intended experience is fixed by design. The layout, interaction model and visual language are not configurable. Colours, fonts and wallpaper may be, mainly so that Windows `.theme` files can be applied.

The project should feel predictable, lightweight, familiar and cohesive.

---

## Design Scope

Daytona aims to be a generally usable, familiar desktop for everyday use, not a pure retro recreation.

* **Windows NT 4.0 is the focus.** When in doubt, do what NT 4.0 did.
* **Anything up to Windows XP with the Classic style is acceptable.** Features, dialogs and behaviours from Windows 98, 2000 and XP (Classic, not Luna) may be used where they improve on NT, provided they are presented in the NT visual language.
* **Minor modern additions are fine.** Small adjustments for things NT never had to deal with (high-density screens, modern Linux desktop conventions, a distribution's own logo, extra wallpaper placement modes such as Fit and Fill) are acceptable when they fit naturally into an existing NT-style dialog or behaviour.

This widens what is eligible; it does not lower the bar for adding things. A feature still needs an explicit request, must fit the NT interaction model and visual language, and must not bring in the larger modern patterns this guide rules out (see Preserve the NT interaction model and Visual Design).

---

## Why this architecture

An earlier direction (Rust, a custom Smithay compositor, GTK4 shell UI) stalled. The lessons that shaped this version:

1. **The compositor is not the product.** Writing a compositor (DRM, input, focus, XWayland, HiDPI, multi-monitor) is most of the work and none of the distinctiveness. labwc already provides a stacking, Openbox-style compositor with server-side decorations, a window menu, Alt+Tab and keybindings.
2. **GTK4 is the wrong fit for the shell UI.** Its rendering is CSS on a GPU scene graph. Qt Widgets paints with `QPainter` through a `QStyle`, which matches Win95-era drawing directly and needs no CSS.
3. **Client-side decorations are not solvable by the shell.** GTK4 / libadwaita header-bar applications draw their own titlebars regardless of toolkit choice. This is accepted as a limitation, not a problem to fight.

Agents must not reintroduce a custom compositor, GTK shell UI, or a different language without explicit instruction.

## Core Principles

### 1. Simplicity is a feature

Prefer the simplest implementation that satisfies the requirement correctly.

Avoid:

* unnecessary abstraction
* speculative extensibility
* plugin systems
* generic frameworks
* configuration options that have not been explicitly requested
* dependency-heavy solutions to small problems
* separate services where a direct implementation is sufficient

A small amount of duplicated straightforward code is preferable to an elaborate abstraction.

### 2. Integrate, don't reimplement

Before writing a component, check whether an established Linux component already does the job well enough:

* compositor and window management: **labwc**
* window decorations: **labwc themes** (generated by Daytona)
* GTK2/3 application look: **Chicago95** GTK theme, icons and cursors
* administrator password prompts (polkit agent): **lxqt-policykit**
* saved passwords (the Secret Service keyring, unlocked at log on by PAM): **gnome-keyring** and **libpam-gnome-keyring**
* old X11 tray icons (XEmbed: GtkStatusIcon, Wine, older Java): Daytona's own small `daytona-xembed-proxy` (KDE's `xembedsniproxy` only comes with most of Plasma, `plasma-workspace`)
* network icon, network password prompts and Network Connections: NetworkManager's **nm-applet** (started with `--indicator` for a StatusNotifierItem icon) and **nm-connection-editor**
* idle timeout, lock before sleep and on logind's `Lock`: **swayidle** (the lock screen itself is Daytona's `daytona-lock`, as no existing locker can show NT's dialogs)
* sound server and volume keys: **PipeWire** (through pipewire-pulse) and **WirePlumber**'s `wpctl`
* sound mixer (Control Panel applet, Open Volume Control): **pavucontrol-qt**
* event sounds: the freedesktop **sound theme** (**sound-theme-freedesktop** by default), played with **libcanberra**
* file dialogs and screen sharing for sandboxed and portal-using applications: **xdg-desktop-portal** with LXQt's (**xdg-desktop-portal-lxqt**) file dialog, **xdg-desktop-portal-wlr** for screen sharing (with Daytona's Share Screen dialog as its chooser) and **xdg-desktop-portal-gtk** for the rest
* Print Screen capture and the clipboard: **grim** and **wl-clipboard**'s `wl-copy`
* suspend, hibernate, lid and power button: **systemd-logind**; battery state: **UPower**; brightness keys: **brightnessctl**
* date, time and time zone: **systemd-timedated** (`org.freedesktop.timedate1`, which asks the polkit agent for the password); network time: whatever NTP service timedated finds (**systemd-timesyncd** on Debian)
* keyboard layouts and switching between them: **XKB**, through labwc's `XKB_DEFAULT_*` environment; the list of layouts: **xkeyboard-config** (`evdev.xml`)
* file manager (folders opened from Run, Documents and other programs) and Find > Files or Folders: **PCManFM-Qt** (never in its `--desktop` mode; the desktop is Daytona's)
* terminal, editor, etc.: existing lightweight applications

Daytona's own code should be the parts that do not exist elsewhere: the NT-style shell UI, the Win95 `QStyle`, the theme converter and the glue that makes them cohesive.

### 3. Do not redesign the project

Agents implement the requested task.

Agents must not independently:

* change the project architecture
* replace major dependencies
* introduce a different UI toolkit
* replace or fork the compositor
* introduce QML / Qt Quick
* introduce new configuration systems
* add extension or plugin architectures
* reinterpret the desktop interaction model
* substantially refactor unrelated code

If a task appears to require an architectural change, stop and explain why. Propose the smallest viable change.

### 4. Preserve the NT interaction model

The desktop follows the Windows NT 4.0 WIMP interaction model, with the additions allowed by Design Scope. Unless explicitly instructed otherwise, assume:

* the taskbar starts at the bottom; when unlocked it can be dragged to any edge of its screen, and when locked it cannot be moved or resized (see Taskbar Placement)
* the Start button is on the left
* the notification area and clock are on the right
* the Start menu opens from the Start button towards the centre of the screen (upward when the taskbar is at the bottom) with a vertical banner and cascading submenus
* each normal top-level window has one taskbar button, in launch order
* clicking a taskbar button activates the window; clicking the button of the active window minimises it
* right-clicking a taskbar button shows the window menu (Restore, Move, Size, Minimise, Maximise, Close)
* the Windows key or Ctrl+Esc opens the Start menu (labwc owns global keybindings; its binding runs `daytona-shell --start-menu`, which asks the running shell over D-Bus to open the menu)
* Alt+Tab switches windows; Alt+F4 closes the active window; Alt+Space opens the window menu
* double-clicking a titlebar maximises/restores
* maximised windows occupy the desktop excluding the taskbar
* right-clicking the desktop shows a desktop context menu

Where behaviour is owned by the compositor (titlebars, borders, Alt+Tab, Alt+Space), Daytona achieves it through labwc configuration it ships, not by reimplementing it.

Minor modern additions are allowed (see Design Scope), but do not introduce modern alternative behaviours that change how the desktop is used unless explicitly requested, for example:

* tiling
* dynamic workspaces
* global menus
* macOS-style window buttons
* overview-driven workflows
* docks
* automatic taskbar grouping
* gesture-first interaction
* search-first Start menus

## Technology Direction

These are project constraints unless a task explicitly changes them.

* **Language:** C++17 (C++20 features only where the target Qt and compilers support them cleanly)
* **UI toolkit:** Qt 6 Widgets. No QML, no Qt Quick, no style sheets for core styling.
* **Compositor:** labwc (wlroots-based), unmodified upstream where possible. **Approved exception:** NT's raised 3D window frame cannot be drawn by any labwc release (borders are one flat colour), so Daytona builds labwc itself: the `third_party/labwc` submodule, pinned to the version Debian 13 ships, plus the minimal patches in `patches/labwc/`, applied at build time by `scripts/build-labwc.sh` without changing the submodule. The result is installed as `libexec/daytona/labwc` and run by the Daytona session. Keep these patches small, theme-option driven and off by default, and offer them upstream; drop each one once a labwc release Daytona can use includes it.
* **Display protocol:** Wayland, with XWayland provided by labwc for X11 applications
* **Shell surfaces:** `wlr-layer-shell` via LayerShellQt
* **Taskbar window list:** `wlr-foreign-toplevel-management-unstable-v1` (and `ext-foreign-toplevel-list-v1` where it adds value), bound through QtWaylandClient
* **Build system:** CMake
* **Primary architectures:** x86_64 and aarch64
* **Initial packaging target:** Debian `.deb`
* **Minimum platform:** Debian 13 (trixie): Qt 6.8, LayerShellQt 6.3 and the labwc version Debian 13 ships. Do not rely on protocols or labwc features newer than that without explicit approval.
* **D-Bus:** QtDBus (part of Qt) for the notification area, notification balloons and logind. No other D-Bus library.
* **Display/login manager:** external existing implementation
* **Session:** a session file that starts labwc with Daytona's labwc configuration, which autostarts the Daytona shell

The shell is a single process unless isolation gives a concrete benefit. The theme converter is a separate command-line tool because it runs rarely and must work without the shell running.

Daytona is **standalone**. It is not a fork of LXQt, lxqt-panel or any other desktop, and it does not link against their libraries. The goal is the smallest shell that delivers NT shell equivalence; general-purpose desktop code brings configurability and dependencies that Daytona deliberately does not want.

Reading other projects for reference (lxqt-panel, Selkies desktop, Chicago95) is encouraged. Copying small pieces of code requires licence compatibility and attribution.

Daytona ships no distribution's logo; it shows what the system has. Without one, or when the user turns it off (Display Properties > Appearance, "Use the operating system's logo on the Start button", on by default, for users whose distribution logo looks poor at 16 pixels), the button shows Daytona's original logo (`artwork/start-logo.svg`).

## Development and Test Environment

A dev container (`.devcontainer/`) based on Debian 13 lets the session run in GitHub Codespaces or locally, without a GPU or physical display:

* labwc runs with the wlroots headless backend and the pixman software renderer (`WLR_BACKENDS=headless`, `WLR_RENDERER=pixman`).
* wayvnc exports the headless output, and noVNC serves it on a forwarded port, so the desktop can be used from a browser.
* `grim` takes screenshots of the headless output for automated smoke tests.

This combination (headless labwc, pixman, a Qt 6 Wayland client with labwc server-side decorations, grim, wayvnc and noVNC) has been run successfully in a plain Linux container. Codespaces itself has not yet been verified.

CI (GitHub Actions) builds Daytona, runs the Qt Test suites and runs a headless session smoke test on every pull request to `main`.

## Compatibility Philosophy

Daytona runs ordinary Linux software. Applications are never required to know about Daytona.

Expected visual results by application type:

| Application type | Frame | Contents |
|---|---|---|
| Qt 5/6 Widgets | labwc server-side, Daytona theme | Daytona Win95 `QStyle` (Qt 6) or nearest equivalent (Qt 5) |
| GTK2 / GTK3 without header bars | labwc server-side | Chicago95 GTK theme with Daytona colours |
| X11 via XWayland | labwc server-side | whatever the application's toolkit provides |
| GTK4 / libadwaita / header-bar apps | client-side, application's own | application's own; **out of scope** |

Do not attempt brittle or application-specific methods to strip client-side decorations or to restyle libadwaita. Compatibility is preferable to visual purity.

Implement standard Wayland protocols rather than application-specific behaviour. Application-specific workarounds require strong justification and a comment explaining when they can be removed.

## Visual Design

The UI should match Windows NT 4.0 closely in structure and feel; later Classic-style details up to Windows XP are acceptable (see Design Scope). Pixel-perfect emulation is not required, and Microsoft artwork, icons, fonts and trademarks must not be copied or shipped.

Characteristics:

* rectangular bevelled 3D borders (raised and sunken)
* solid colours, no gradients except titlebar gradients where the colour scheme or `.theme` specifies them (as Windows 98, 2000 and XP Classic did)
* conventional titlebars, menus and dialogs
* simple pressed / unpressed button states
* dotted focus rectangles
* compact, mouse-and-keyboard information density
* no animation by default

Do not introduce:

* rounded corners
* translucency or blur
* drop shadows
* large touch-first controls
* floating panels
* oversized whitespace
* transitions

All shell drawing goes through the Win95 `QStyle` and the current `QPalette`, so a theme change restyles the shell without code changes. Do not hard-code colours in widgets.

---

## The Win95 QStyle

The style is a Qt 6 style plugin (subclass of `QCommonStyle`, or `QProxyStyle` over the built-in Windows style if that proves simpler and remains correct).

* It draws with `QPainter` primitives only. No images for basic controls, no style sheets.
* It takes all colours from `QPalette`. The theme converter is responsible for producing the palette.
* It must be usable by third-party Qt 6 applications via `QT_STYLE_OVERRIDE` or qt6ct, not just the shell.
* Bevel widths and metrics must scale with device pixel ratio.

## Theme Compatibility

Daytona supports Windows 95 / Plus! era `.theme` files as its colour and appearance format.

The theme tool:

1. Parses a `.theme` file (INI format) as untrusted input.
2. Extracts colours (`[Control Panel\Colors]`), wallpaper, fonts and, where present, cursors, icons and sounds.
3. Generates:
   * a labwc theme (`themerc` and button images) for window frames
   * a Qt palette / colour scheme consumed by the shell and the `QStyle`
   * a GTK3 colour override for the Chicago95 theme
   * wallpaper and cursor settings for the session
4. Writes into the user's data directories only, never system directories.

Rules:

* Missing keys fall back to the Windows Standard scheme.
* Unknown keys are ignored, not errors.
* Paths inside `.theme` files are Windows paths; map them relative to the theme file and never follow them outside the theme's own directory.
* Unsupported elements (e.g. screensavers, sounds if no sound support exists) are reported, not silently dropped.
* Chicago95 Plus! is prior art; reuse its knowledge where licences allow.

Daytona's own settings are a small, documented INI file, not CSS and not a generic theme engine.

## Configuration Policy

Daytona is deliberately not customisable beyond what the Windows shell offered.

The rule: **a setting is eligible only if the Windows shell offered it between NT 4.0 and XP (Classic), or it is a minor modern addition that fits an existing NT-style dialog (see Design Scope).** Being eligible does not make a setting required; it is only added when explicitly requested.

Accepted configuration, Display Properties equivalents:

* colour scheme and fonts (normally applied via `.theme` files)
* wallpaper
* the Start button logo: the operating system's or Daytona's
* desktop area (resolution) and refresh frequency, per screen, on the Settings tab as in NT (applied through wlr-output-management, confirmed by a 15-second keep-or-revert prompt instead of NT's Test button, and remembered per screen like the font size)
* monitor arrangement, on the Settings tab with more than one monitor, as Windows 2000 had it: the numbered monitor diagram (drag to arrange, snapping edge to edge), the Display list, "Use this device as the primary monitor" (the taskbar's monitor) and "Extend my desktop onto this monitor" (on/off). Applied through wlr-output-management with the same keep-or-revert prompt and remembered per screen. Mirroring and a taskbar per monitor are out of scope. See `docs/multi-monitor.md`.
* clock format (follows the system locale)
* the screen saver, on NT's Screen Saver tab: (None) or Blank Screen, Wait 1-60 minutes, and Password protected (default Blank Screen, 15 minutes, not protected). Animated screen savers and NT's other savers are out of scope.
* high-contrast schemes and font size, as accessibility options. Font size is NT's Settings tab choice (Small Fonts 100%, Large Fonts 150% rather than NT's 125%, as the more useful size on today's high-density screens, with 125% still available under Custom..., custom 100-300%), applied as each screen's scale through wlr-output-management and remembered per screen.

Accepted configuration, Mouse Properties equivalents (NT's Control Panel applet, approved as a dialog):

* the pointer scheme on the Pointers tab: Standard, Standard (large) and Standard (extra large), as NT offered for Windows Standard. It is applied at the next log on (daytona-session sets `XCURSOR_SIZE` 32, 64 or 96). NT's Buttons, Motion and General tabs are not offered.

Accepted configuration, Keyboard Properties equivalents (NT's Control Panel applet, approved as a dialog, issue #110):

* the input locales on the Input Locales tab: installed keyboard layouts (any XKB layout or variant xkeyboard-config lists, added by language as NT's Add Input Locale did), the default one, and the Switch locales hot key (Left Alt+Shift, the default, Ctrl+Shift or None, done by XKB's `grp:alt_shift_toggle` and `grp:ctrl_shift_toggle`). Until something is chosen the system's keyboard is used (`/etc/default/keyboard`, as the installer set it), and the system's other XKB options are always kept. NT's Speed and General tabs are not offered.

Accepted configuration, Date/Time Properties equivalents (NT's Control Panel applet, opened by double-clicking the clock, issue #3):

* the date and time on the Date & Time tab, the time zone on the Time Zone tab (a list in place of NT's world map) and Windows 2000's network time ("Automatically synchronise with an Internet time server", one check box). These are system settings, kept by systemd-timedated, not in Daytona's INI file. NT's "Automatically adjust clock for daylight saving changes" is not offered (the time zone always does), nor XP's Internet Time tab (choosing time servers).

Accepted configuration, Sounds Properties equivalents (NT's Control Panel applet, issue #15):

* the sound theme (NT's sound scheme), or No sounds: the desktop-wide freedesktop setting, not Daytona's INI file (see Sounds)
* a sound file, or none, for each of the shell's events, in `[Sounds]`

Accepted configuration, Taskbar Properties equivalents:

* taskbar edge (set by dragging, not by a setting in a dialog)
* lock the taskbar (from Windows XP; makes drag-to-edge safe to leave enabled)
* always on top
* auto hide
* show small icons in Start menu
* show clock

Accepted configuration, INI file only (no dialog):

* `StartMenu/FlatPrograms`: Start > Programs as one alphabetical list of every program, without folders (requested on issue #5; off by default, when folders come from the freedesktop menu file).
* `Lock/DisableCtrlAltDelete`: every lock opens on Unlock Workstation instead of asking for Ctrl+Alt+Delete first, as NT's `DisableCAD` policy (requested on issue #23; off by default).

Settings are stored with `QSettings` in a single INI file. No other configuration mechanism is used.

Fixed:

* taskbar contents and their order
* Start menu structure
* titlebar button order
* interaction model

Do not add settings outside Design Scope, such as taskbar transparency, alternative Start menu layouts, panel applets or custom widgets. Do not expose a setting simply because it is easy to implement.

## Start Menu

Top to bottom, matching NT 4.0:

* **Programs**: cascading submenus built by the freedesktop Desktop Menu Specification from `${XDG_MENU_PREFIX}applications.menu` (daytona-session sets the prefix to `daytona-`; Daytona ships `/etc/xdg/menus/daytona-applications.menu` with one folder per freedesktop main category, NT's names where NT had one, such as Accessories, and a built-in copy for when no menu file is installed). Distribution and administrator additions in `applications-merged/`, `.directory` folder names and menu editors' changes in `~/.config/menus` all apply, and the menu is rebuilt when they change. Daytona reads the menu files itself (`shell/xdgmenu.cpp`, Qt XML): LXQt's `libqtxdg` is ruled out below, libmenu-cache needs its own daemon, and GNOME's libgnome-menu brings GObject file monitoring the off-UI-thread scan cannot use. Every folder has the same program-group icon (`applications-other`), as NT's program groups did, whatever the `.directory` file says; programs keep their own icons. Folders come first, then programs, alphabetical within each unless the menu file has a `<Layout>`; empty folders are omitted. Entries with `NoDisplay=true`, `Hidden=true`, `OnlyShowIn`/`NotShowIn` excluding Daytona, or a missing `TryExec` program are omitted. `StartMenu/FlatPrograms=true` in the INI file (no dialog) lists every program in Programs itself instead, without folders.
* **Documents**: the 15 most recent items from `~/.local/share/recently-used.xbel`.
* **Settings**: Control Panel (see Control Panel below), Taskbar... (Taskbar Properties), Display... (Display Properties, colours/wallpaper/`.theme`), Keyboard... (Keyboard Properties, input locales), Mouse... (Mouse Properties, pointer scheme).
* **Find**: Files or Folders... launches the file-search command set in Daytona's INI file (`Commands/Find`), else PCManFM-Qt's Find Files (`pcmanfm-qt --find-files ~`) when it is installed; greyed out if neither.
* **Run...**: Daytona's Run dialog.
* separator
* **Shut Down...**: NT-style dialog offering Shut down, Restart and Close all programs and log on as a different user, using systemd-logind over QtDBus, plus Stand by and Hibernate (see Power) and Lock the computer (see Screen Lock and Screen Saver). Shut down and Restart are disabled when logind reports them unavailable, as NT did; Stand by and Hibernate are shown only where logind allows them. Before shutting down, restarting or logging off, every program is asked to close, as NT did (the shell sends Close to each owner window over the foreign-toplevel protocol and waits), so programs can save their work or ask to; one that has not closed after 20 seconds gets NT's End Task prompt (End Task, Wait, Cancel), which goes away by itself if the program closes meanwhile. End Task stops waiting for that program, which ends with the session.

NT's **Help** item is omitted; there is no system-wide help viewer to open.

## Control Panel

Start > Settings > Control Panel opens NT's Control Panel: a folder window of applet icons, with File (Open, Close) and View (Status Bar, Large Icons, Small Icons, List, Refresh) menus and a status bar showing the object count or the selected applet's description.

* Applets are shown under two headings, drawn like Windows XP's "Show in Groups": **Daytona** (the shell's own dialogs: Date/Time, Display, Keyboard, Mouse, Sounds, System, Taskbar), then **Applications**.
* **Applications** lists every installed application the Start menu would show whose `.desktop` file has `Settings` in `Categories`. This is the registration mechanism: an application adds a Control Panel applet with a standard freedesktop `.desktop` file, and the list follows installs and removals. There is no Daytona-specific applet API or plugin system.
* Opening a Daytona applet opens its dialog in the shell; opening an application launches it as the Start menu does.
* A new Daytona settings dialog is added to the Daytona group as well as (where NT had one) its own Start > Settings item.

## System Properties

NT's Control Panel > System, also opened from My Computer > Properties on the desktop and by Win+Pause (a labwc keybinding running `daytona-shell --system-properties`). Read-only; everything is read once when it opens, from files that need no root (`shell/systeminfo.*`):

* **General** tab, laid out as Windows 98's: Chicago95's `computer` icon (My Computer's, from its scalable SVG at 96 pixels; never a Windows flag or other Microsoft logo) beside four groups. **System:** the distribution (os-release's `PRETTY_NAME`, else `NAME` and `VERSION`), `Daytona <version>` and the kernel (`uname`, as Windows showed its build number). **Registered to:** the user's full name (GECOS, else the login name). **Computer name:** `PRETTY_HOSTNAME` from `/etc/machine-info`, else the host name. **Computer:** the processor's vendor and model from `/proc/cpuinfo` (x86's `vendor_id` and `model name`; ARM's implementer and core names from a table of the common ones, both kinds of a big.LITTLE processor; RISC-V's `uarch`, POWER's `cpu`; else `Hardware`, the devicetree or DMI model, then `uname -m`), the number of logical processors when more than one, and `MemTotal` as "x.x GB RAM" (1024-based as Windows counted, one decimal, not rounded up to the installed amount; MB under 1 GB).
* **Performance** tab: memory (total, and in use as `MemTotal - MemAvailable`) and virtual memory (swap total and in use from `/proc/meminfo`, with a bar for each), and the swap partitions, files and zram devices from `/proc/swaps`, or "Virtual memory is disabled" when there are none. Windows 98's System Resources, File System, Graphics and Virtual Memory settings have no Linux equivalent or need root, and are not offered.
* NT's Environment, Startup/Shutdown and User Profiles tabs, and Windows 98's Device Manager and Hardware Profiles, are not offered.

## Taskbar Window Menu

Right-clicking a taskbar button shows Restore, Move, Size, Minimise, Maximise, separator, Close (Alt+F4), drawn by the shell with the Win95 `QStyle`.

* Restore, Minimise, Maximise and Close use foreign-toplevel requests. Items that do not apply to the window's current state are disabled, as in NT.
* **Move and Size are always shown disabled.** foreign-toplevel has no request to start an interactive move or resize. They remain available from the titlebar window menu (Alt+Space), which labwc draws. Adding the capability is an upstream labwc/protocol matter, not something to work around in the shell.

## Notification Balloons

The shell implements the `org.freedesktop.Notifications` D-Bus service.

* Each notification appears as a Windows 2000-style balloon pointing at the notification area: yellow tooltip background (`QPalette::ToolTipBase`), bold title, body text, optional icon, close button.
* One balloon at a time; further notifications queue.
* A balloon closes on click, on its close button, or after its timeout: the application's (at most 60 seconds), else 10 seconds for `-1`. Clicking the body invokes the `default` action if present.
* **Balloons that stay:** a timeout of `0` or urgency critical (`2`) never expires, as the specification says; it stays until the user or the application closes it. It does not hold the queue: after 10 seconds (Windows 2000's minimum balloon time) a waiting notification takes its place, or the next one to arrive does at once, and the staying balloon goes to the back of the queue, still open, to show again when its turn comes. Windows 2000 and XP likewise let a newer balloon replace the current one once it had been up for the minimum time. Nothing is closed or lost by giving way.
* **Time nobody can see does not count:** while the session is locked or the Blank Screen screen saver is showing, the shown balloon's time stands still (Windows 2000 did not count idle time towards a balloon). Plain idle time without a screen saver still counts, since the shell has no idle signal then.
* Supported capabilities: `body`, `actions` (default action only), `icon-static`, `sound` (see Sounds). Markup and persistence are not supported.
* No notification history, do-not-disturb or notification centre: none existed up to Windows XP.

## X11 Tray Icons

Programs that only know the X11 system tray (XEmbed) get their icons in the notification area through `daytona-xembed-proxy` (`xembed/`, installed in `libexec/daytona`), the X11 tray on the Xwayland display, which shows each docked icon as a StatusNotifierItem (see `docs/third-party-apps.md`).

* It is a separate process because it must be an X11 client: when Xwayland goes, its clients go with it, and the shell must not. labwc's autostart starts it only when Xwayland is installed and `DISPLAY` is set; it ends with the X display.
* Icons are read at NT's 16 pixels from each icon window's own pixmap (Composite, updated on Damage), and keep their transparency (the tray offers a 32-bit visual).
* Clicks are sent to the icon as core events (entering, press, release, leaving) with the X11 pointer and the hidden icon moved under the click; XTEST does not reach X11 windows on Xwayland while the compositor's pointer is over the taskbar. While a menu it opened is showing, a transparent X11 window under it takes clicks elsewhere, so the menu closes.
* The shell gives tray items the click position in the compositor's layout, just outside the taskbar's inner edge, so programs open their menus beside the taskbar (Qt does not know a layer-shell surface's position).

## Volume Control

NT 4.0's speaker icon in the notification area, built into the shell (no existing tray application offers NT's pop-up):

* The speaker sits between the tray icons and the clock, and shows whether the default output is muted. It is hidden while there is no sound server or output.
* Clicking it opens NT's volume pop-up: "Volume", a vertical trackbar (0-100%) and a Mute check box, changing the default output. Double-clicking it, or Open Volume Control on its right-click menu, starts the installed mixer (pavucontrol-qt, else pavucontrol).
* The shell talks to the sound server with libpulse on Qt's GLib event loop, and follows changes made elsewhere (keys, mixers) through PulseAudio's change subscription. Nothing is polled.
* The volume keys (`XF86AudioRaiseVolume`, `XF86AudioLowerVolume`, `XF86AudioMute`, `XF86AudioMicMute`) are labwc keybindings running `wpctl`; raising stops at 100%.
* The Control Panel's sound applet is the mixer's own `.desktop` file (pavucontrol-qt lists `Settings`), not a Daytona dialog.
* Event sounds and NT's Sounds applet are separate (see Sounds).

## Sounds

NT's system sounds and Control Panel > Sounds, in freedesktop terms so that one setting serves Daytona and every other program (issue #15):

* **Events are freedesktop sound names** (Sound Naming Specification), shown by those names in Sounds Properties and grouped as the specification groups them: Alerts (`battery-low`, `dialog-error`) and Notifications (`battery-caution`, `bell`, `desktop-login`, `desktop-logout`, `dialog-information`, `dialog-question`, `dialog-warning`, `message-new-instant`). Where the theme lacks a name the shell tries another: `desktop-login`/`desktop-logout` play `service-login`/`service-logout`, `dialog-question` `window-question`, `battery-caution`/`battery-low` `dialog-warning`/`dialog-error` (the freedesktop theme has none of the first ones).
* **When they play:** `desktop-login` once a session (labwc's process id is noted in `$XDG_RUNTIME_DIR/daytona-logon-sound`, so a restarted shell stays quiet); `desktop-logout` after programs have closed for Log off, Shut down or Restart, the session ending once it has played (at most 10 seconds); every message box the shell shows plays its icon's sound (`dialog-error`, `dialog-warning`, `dialog-information`, `dialog-question`, `bell` without an icon), as NT did; low battery balloons play `battery-caution` (low) or `battery-low` (critical); notification balloons play their `sound-file` or `sound-name` hint, nothing with `suppress-sound`, otherwise `message-new-instant` for a new notification (not for updates to one). Daytona does not see devices being added or removed, so it plays no `device-added`/`device-removed`.
* **Playback** is libcanberra, the specification's reference implementation (theme lookup and inheritance, and decoding the Ogg Vorbis files themes ship; the shell's libpulse could not decode them), through its PulseAudio backend.
* **The sound theme** is the desktop-wide setting: GTK's `gtk-sound-theme-name` and `gtk-enable-event-sounds` in `settings.ini`, and GSettings' `org.gnome.desktop.sound` `theme-name` and `event-sounds` (written with `gsettings` when it is installed), which GTK 3 on Wayland, libcanberra's GTK module and GSound read. The shell reads `settings.ini`, else GSettings, else uses `freedesktop`.
* **Sounds Properties** (Control Panel > Sounds; NT had no Start menu item for it) has NT's layout: the Events list (selecting one shows its description), the selected event's sound (Name: `(None)`, the theme's sound files, or a file chosen with Browse..., and Preview), and **Sound theme** in place of NT's Schemes: the installed themes ("Name (id)") and "No sounds", which turns event sounds off. As NT's schemes did, choosing a theme gives every event that theme's sound again. A sound chosen for one event, or `(None)`, is kept in Daytona's INI file (`[Sounds]`, by sound name) and applies to the shell's own sounds only; other programs use the theme. NT's Save As and Delete scheme buttons are not offered.
* The mixer stays the Control Panel's "Sound" application (pavucontrol-qt, under its own name), as NT had Sounds beside Multimedia.
* **Sound files:** Daytona ships none. Chicago95's sound theme is not installed: it is built from Windows 95's sounds (its commit says so, and `Extras/` holds the Windows 95 startup sound). The package recommends `sound-theme-freedesktop`.
* Not provided: per-application sounds, NT's Multimedia applet, sound recording.

## Input Locales

NT's Keyboard Properties (Input Locales tab) and its input locale indicator:

* labwc builds its keymap from `XKB_DEFAULT_MODEL`, `_LAYOUT`, `_VARIANT` and `_OPTIONS`, read from an `environment` file in its configuration directory. daytona-session gives labwc a directory of the session's own (`$XDG_RUNTIME_DIR/daytona-labwc`: links to the installed `rc.xml`, `menu.xml` and `autostart`, plus that file, written by `daytona-shell --labwc-environment`) and exports it as `DAYTONA_LABWC_CONFIG`.
* Applying Keyboard Properties saves the locales (`[Keyboard] Layouts`, `Hotkey`), rewrites the environment file and sends labwc SIGHUP (as `labwc --reconfigure` does), so the change applies at once and at every later log on.
* XKB switches layouts itself on the hot key. The indicator ("En", "De": the layout's language in the selection colours) follows the keyboard's layout group, which labwc sends with the keyboard modifiers to every client, focused or not; the shell reads it from its own `wl_keyboard`. It is shown only while more than one locale is installed.
* Clicking the indicator lists the locales; choosing one gives labwc the layouts again starting with it, as no protocol lets a client set the group. Its right-click menu opens Keyboard Properties.
* Input methods (IBus, Fcitx) are out of scope.

## Date and Time

NT's Date/Time Properties, opened by double-clicking the clock or from the Control Panel:

* Date & Time tab: Date (month, year and NT's month calendar, a `QCalendarWidget` without its navigation bar, every day drawn alike) and Time (NT's analogue clock face, drawn with `QPainter` from the palette, over a time field with seconds), Windows 2000's network time check box, and the current time zone's name. The time runs while the dialog is open and stops once the date or time is changed by hand; while network time is on, the date and time cannot be changed (timedated refuses to set the clock then).
* Time Zone tab: the zones in tzdata's `zone1970.tab`, plus UTC, listed as "(GMT+01:00) Europe/Paris" in order of their standard (winter) offset, as NT ordered its list.
* Apply sends only what changed, to systemd-timedated over the system bus: SetNTP, then SetTimezone, then SetTime (the date and time as shown, in the chosen zone), asynchronously and interactive, so the polkit agent asks for an administrator's password. The first refusal stops the rest and is shown; OK closes the dialog once everything has been applied.
* The shell follows timedated's PropertiesChanged signal, so a time zone set anywhere (this dialog, `timedatectl`) moves the taskbar clock at once: it makes glibc read the zone again (glibc otherwise keeps the zone it first read while `TZ` is unchanged) and redraws the clock.

## Screen Lock and Screen Saver

* **Lock Workstation** is Win+L (from Windows XP; a labwc keybinding running `daytona-shell --lock`) and "Lock the computer?" in the Shut Down dialog (NT kept it in Ctrl+Alt+Del's Windows Security dialog, which Daytona does not have). The shell runs `daytona-lock` (installed in `libexec/daytona`), a Qt client of `ext-session-lock-v1`: the desktop colour with NT's "Workstation Locked" dialog drawn on it (a lock surface cannot have windows, so the dialog frame and title bar are painted). Ctrl+Alt+Delete opens "Unlock Workstation" (user name and password, OK and Cancel); a wrong password shows NT's warning, and a minute without input returns to Workstation Locked. With `Lock/DisableCtrlAltDelete=true` in the INI file (no dialog, NT's `DisableCAD`), the shell passes `--no-ctrl-alt-delete` and every lock (Win+L, Shut Down, before sleep, logind's `Lock`, the password-protected screen saver) opens on Unlock Workstation with the password box focused; Cancel, Escape and the minute without input return to it with the password cleared, so Workstation Locked never shows. Passwords are checked with PAM service `daytona` (`/etc/pam.d/daytona`, from the package; `login` if missing). The locker prints `locked` once the compositor has locked the session and exits once unlocked. It is a separate process, so the lock holds if the shell exits; if it crashes, labwc keeps the session locked and the shell starts it again (at most 5 times a minute) to take the lock over. It uses Qt's private Wayland client API (a shell integration, as LayerShellQt does), so it is tied to the Qt version it was built with.
* **The screen saver** is Display Properties' Screen Saver tab. The shell runs `swayidle` with the wait as its timeout, restarting it when the settings change (swayidle cannot change its timeouts while running). The timeout runs `daytona-shell --screen-saver`: Blank Screen covers every screen with a black overlay layer surface that ends when the pointer moves or a key or button is pressed; Password protected starts `daytona-lock --screen-saver` instead, which stays black with no pointer until a key is pressed or the pointer moves, then shows Workstation Locked. Preview shows Blank Screen.
* **Locking for the system**: swayidle also runs `daytona-shell --lock` before sleep (waiting until the screen is locked) and on logind's `Lock` signal (`loginctl lock-session`).
* **Keeping the screen on**: swayidle honours Wayland's idle-inhibit protocol. The shell also serves `org.freedesktop.ScreenSaver`'s `Inhibit`/`UnInhibit` (on `/org/freedesktop/ScreenSaver` and `/ScreenSaver`), which VLC, LibreOffice Impress and others use instead; while any inhibit is held swayidle runs without its timeout. An inhibit ends with `UnInhibit` from the same caller or when the caller leaves the bus.
* Not provided: animated screen savers, NT's Windows Security dialog (Ctrl+Alt+Del outside the lock screen) and monitor power saving.

## Power

Laptop support from Windows 98 and 2000, on top of logind and UPower:

* **Stand by and Hibernate** are in the Shut Down dialog ("Put the computer on stand by?", "Hibernate the computer?"), shown only when logind's `CanSuspend` / `CanHibernate` answer `yes` or `challenge`, and call logind's `Suspend` / `Hibernate` asynchronously like the other options. The screen is locked before the machine sleeps (swayidle's `before-sleep`, see Screen Lock and Screen Saver), so the session is locked on resume.
* **The battery icon** is Windows 2000's power meter, built into the shell (the existing tray battery monitors are GTK or XEmbed, or bring LXQt's power manager with its own idle and lid handling). It follows UPower's display device over QtDBus, re-reading it on UPower's `PropertiesChanged`, and is hidden on machines without a battery. It sits left of the speaker; the icon shows the charge and a plug while on mains power, and the tooltip the charge and time left as Windows XP worded it ("1 hr 23 min (45%) remaining", "45% available (plugged in, charging)").
* **Low battery**: when UPower's warning level rises to low or critical while on battery, a balloon says so (a critical one is sent as critical and stays until closed). UPower's own critical action (hibernate or power off) is left to UPower.
* **Brightness keys** (`XF86MonBrightnessUp/Down`) are labwc keybindings running `brightnessctl`, which writes the backlight as a member of the `video` group (Debian's `brightness-udev`); lowering stops at 1, so the backlight never goes fully off.
* Not provided: power plans, NT/2000's Power Options dialog, lid and power button policy (logind's) and keyboard backlight.

## Print Screen

* **Print Screen** copies every screen to the clipboard as a PNG at device resolution, as NT did: no dialog, no file. **Alt+Print Screen** copies the screen the active window is on (every screen when no window is active). NT copied only the active window, but labwc 0.8.3 gives clients neither window geometry (foreign-toplevel has none) nor a way to capture one window (that needs wlroots 0.19's toplevel capture source); revisit when Daytona moves to a labwc that offers it.
* Both are labwc keybindings running `daytona-shell --print-screen` / `--print-window`. The running shell knows which screen the active window is on (foreign-toplevel's `output_enter`), runs `grim`, and passes the image to `wl-copy` only once grim has succeeded, so a failed capture leaves the clipboard alone.
* For scripts (diagnostics, documentation screenshots), both take an optional file name and save the PNG there instead; the command returns once the image is in place and fails if it could not be captured.
* Not provided: a screenshot application, region selection, or saving key-press captures to a folder.

## Desktop

The desktop is a background layer-shell surface on each output showing the wallpaper or desktop colour, with a right-click menu whose **Properties** opens Display Properties.

The primary monitor's desktop (the taskbar's) also shows NT's desktop icons (issue #2, approved). Daytona draws them itself; PCManFM-Qt's `--desktop` mode is never used, because it covers Daytona's wallpaper and has LXQt's menus, not NT's. Everything beyond the desktop's own small set of operations is handed to the file manager through standard formats, so the two never conflict:

* **Icons:** My Computer, Network Neighborhood and Recycle Bin (empty or full) at the top left, then the files and folders in the XDG Desktop directory (`~/Desktop`), in NT's grid of columns from the top left, kept clear of the taskbar. Hidden files are not shown. Icons are Chicago95's system icons (MIME types, places); `.desktop` files show their own Name and Icon, as NT showed a shortcut's, and applications' icons are never replaced. Labels are drawn in the scheme's colours, NT's way.
* **Opening:** double-click or Enter. My Computer, Network Neighborhood and Recycle Bin open `computer:///`, `network:///` and `trash:///` in PCManFM-Qt (the home folder, nothing and the trash folder through `xdg-open` without it). Files and folders open with `xdg-open`, so folders go to PCManFM-Qt (`daytona-mimeapps.list`); `.desktop` files are launched as the Start menu launches them.
* **Selection and placement, as NT:** click selects, Ctrl+click adds, a rubber band selects several, arrow keys move between icons, typing a letter selects the next icon starting with it. Dragging moves icons anywhere on the desktop; positions are remembered per name in Daytona's INI file. Dragging between the desktop and other programs is not provided.
* **Desktop menu:** Arrange Icons (by Name, Type, Size, Date; Auto Arrange), Line up Icons, Paste, Paste Shortcut, New (Folder, Text Document), Properties. NT's Undo and New > Shortcut (a wizard) and Briefcase are not offered.
* **Icon menu:** Open (bold), Cut, Copy, Create Shortcut, Delete, Rename for files; Open and Properties (System Properties) for My Computer; Open for Network Neighborhood; Open and Empty Recycle Bin for the Recycle Bin. NT's Properties sheets for files and Network Neighborhood are not offered; PCManFM-Qt has its own.
* **File operations stay standard:** Delete moves to the freedesktop trash (with NT's confirmation), so items appear in PCManFM-Qt's Trash and can be restored there. Cut, Copy and Paste use `text/uri-list` with `x-special/gnome-copied-files`, so they work both ways with PCManFM-Qt and other file managers. A shortcut is a symbolic link ("Shortcut to X"). A pasted item that would replace one gets NT's "Copy of X" name instead. Rename is in place (F2 or the menu). Copying shows no progress dialog; large copies belong in the file manager.
* The desktop follows changes to `~/Desktop` and the trash made by any program, through a file watcher, reading the folder off the UI thread.

Not provided: Active Desktop, web content on the desktop, icons on other monitors, the Briefcase, and NT's icon spacing settings.

## Taskbar Placement

The taskbar behaves like the Windows taskbar:

* By default it is docked to the bottom edge and **locked**.
* "Lock the taskbar" is a checkable item in the taskbar's right-click menu and in Taskbar Properties.
* While unlocked, the user presses on an empty area of the taskbar and drags. The taskbar snaps to the screen edge nearest the pointer (bottom, top, left or right) and stays there on release. There is no free-floating position.
* While unlocked, the user can drag the taskbar's inner edge to change its thickness in whole rows (horizontal) or to a wider width (vertical), as in NT. It cannot be made thinner than one row.
* While locked, dragging and resizing do nothing.
* Edge and thickness persist across sessions.
* On a vertical edge, contents stack vertically: Start button at the top, window buttons below, notification area and clock at the bottom.

Implementation constraints (no new dependencies):

* Placement uses only `wlr-layer-shell` through LayerShellQt: anchors select the edge, the exclusive zone reserves space so labwc keeps maximised windows clear of the taskbar, and the surface size sets thickness. Changing edge means updating anchors, exclusive zone and size, then re-laying out the widgets.
* Dragging relies on the standard Wayland implicit pointer grab: after a button press on the taskbar, motion events keep arriving at the taskbar surface even outside its bounds. The nearest edge is computed from that position and the output geometry Qt reports. Verify this behaviour in labwc before building on it; if it does not hold, stop and report rather than adding a workaround.
* Layout direction is switched with standard Qt layouts (`QBoxLayout::setDirection`), not separate horizontal and vertical widget trees.
* "Always on top" maps to the layer-shell `top` layer, otherwise `bottom`. "Auto hide" sets the exclusive zone to zero and shrinks the surface to a thin strip that expands on pointer entry.
* The taskbar stays on its own output: the primary monitor chosen in Display Properties (see `docs/multi-monitor.md`). Dragging it to another monitor is out of scope.

## Performance Philosophy

Daytona targets ordinary and low-end systems, in the spirit of the original NT shell. Small is a goal in its own right: binary size, resident memory, dependency count and lines of code should all stay as low as correctness allows.

* The shell should idle at near-zero CPU. No polling and no permanently running timers (the clock timer fires once per minute, aligned to the minute).
* Avoid loading Qt modules the shell does not need (no Qt Quick, no WebEngine, no Multimedia).
* Prefer one process.
* Cache `.desktop` file parsing; refresh on filesystem change notification, not by rescanning on a timer.
* Do not perform filesystem scanning, icon decoding or process waiting on the UI thread when it can block noticeably.

Correctness comes before premature optimisation. Performance claims must be measured.

---

## HiDPI and Multi-Monitor

* Never assume logical pixels equal physical pixels. Use Qt's device-independent pixels and device pixel ratio throughout, including in the `QStyle`.
* Bevels and 1-pixel lines must stay crisp at integer scales and acceptable at fractional scales.
* Do not assume a single output. The taskbar is placed on the primary output initially; the design must not prevent a taskbar per output later.

## C++ and Qt Guidelines

Prefer clear, conventional modern C++ and idiomatic Qt.

Prefer:

* Qt parent-child ownership for widgets; `std::unique_ptr` for non-QObject ownership
* signals and slots for UI events
* `enum class` for meaningful states
* small focused classes and files
* descriptive names
* `const` correctness

Avoid unless justified:

* raw `new` / `delete` outside Qt parent ownership
* deep inheritance hierarchies
* template metaprogramming
* macros beyond those Qt requires
* exceptions crossing Qt event boundaries
* `QWidget::setStyleSheet` for core styling

Compile with warnings enabled (`-Wall -Wextra`) and treat new warnings as defects. Format with clang-format using the repository's configuration.

## Error Handling and Logging

* A failure in one shell component must not take down the whole shell.
* If a Wayland protocol the shell relies on is missing, log a clear warning and degrade (e.g. taskbar without window buttons) rather than crash.
* Use `QLoggingCategory` with per-component categories (`daytona.taskbar`, `daytona.startmenu`, etc.).
* Do not leave temporary debug output in committed code.
* Never show internal error messages or stack traces in user-facing dialogs.

---

## Window State

The compositor is the source of truth for window state.

The taskbar reflects state reported through foreign-toplevel (title, app id, activated, minimised, maximised) and requests changes through the same protocol. It never tracks its own contradictory copy of window state.

---

## Security Boundaries

Treat application metadata, `.desktop` files and `.theme` files as untrusted input.

* Window titles and app ids are not safe for shell execution or file paths.
* Launch applications with `QProcess::startDetached` and structured arguments, following the Desktop Entry `Exec` field-code rules. Do not use `/bin/sh -c` unless shell semantics are explicitly required (e.g. the Run dialog, where the user is typing a command).
* The Run dialog runs as the user; it is not a privilege boundary.
* The session runs as the normal user. No setuid, no root helpers.

---

## Accessibility

* Every shell function is reachable by keyboard (Start menu navigation, taskbar focus, Run dialog).
* Focus is always visible (dotted focus rectangle).
* Set accessible names on shell widgets.
* Colour is never the only indicator of state.
* High-contrast `.theme` files must render correctly.

## Testing Expectations

Prefer automated tests (Qt Test) for:

* `.theme` parsing and colour conversion
* labwc theme / Qt palette / GTK output generation
* `.desktop` parsing and building Start > Programs from menu files
* `Exec` field-code expansion
* taskbar ordering and state transitions given toplevel events
* geometry and scaling calculations in the style

Keep Wayland-dependent code thin so the logic beneath it is testable without a compositor.

Graphical changes should, where practical, extend the headless smoke test (start the session headless, launch the shell, take a `grim` screenshot and check something concrete, such as the taskbar's reserved area or a pixel colour at a known position). Avoid brittle whole-image comparisons.

For graphical changes, also provide a concise manual checklist (the Codespaces noVNC session is suitable), for example:

* launch labwc with the Daytona session and two applications
* click each taskbar button; click the active one to minimise
* right-click a taskbar button and use each window menu item
* open the Start menu with the mouse, the Windows key and Ctrl+Esc; navigate it with arrow keys
* apply two different `.theme` files and confirm shell, frames and a Qt app all change
* unlock the taskbar, drag it to each edge, maximise a window each time and confirm the window clears the taskbar; lock it and confirm it no longer moves
* test at 1× and 2× scale

## Never Fake Success

Do not claim:

* code compiles when it was not compiled
* tests pass when they were not run
* a feature works when it was not exercised
* protocol behaviour that has not been verified
* performance improvements that were not measured

If the environment prevents verification (for example, no Wayland session is available), say so. Partial verification is acceptable; false confidence is not.

Wayland protocols, labwc, Qt, LayerShellQt and the `.theme` format all have subtle behaviour.

* Consult current documentation and protocol XML.
* Check the version actually targeted.
* Do not invent API methods or configuration keys.
* Distinguish between protocol requirement, library behaviour, labwc behaviour, Windows behaviour and Daytona policy.

## Decision Rule

When several reasonable implementations exist, prefer the one that is:

1. correct
2. standards-compliant
3. already provided by an existing component
4. easy to understand and review
5. lightweight
6. easy to test
7. boring

A desktop shell is infrastructure. Users should notice their applications, not the shell.
