# AGENT.md

## Project Overview

Project Daytona is a Windows 95 / Windows NT 4.0 style desktop shell for Linux.

It is a **shell**, not a compositor and not a toolkit. It provides the desktop experience on top of an existing Wayland compositor:

* Taskbar (bottom by default, movable when unlocked)
* Start button and Start menu
* Taskbar window buttons
* Notification area and clock
* Notification balloons (Windows 2000 style)
* Desktop background and desktop context menu
* Run and Shut Down dialogs
* Window switching UI where the compositor does not already provide it
* A Win95-style Qt widget style
* A Windows `.theme` (Plus! 95 era) converter

Window management, window decorations, input and output handling are delegated to the compositor (labwc). Where the compositor's behaviour differs from NT, the preferred fix is a configuration change or an upstream contribution to the compositor, not a replacement compositor.

The intended experience is fixed by design. The layout, interaction model and visual language are not configurable. Colours, fonts and wallpaper may be, mainly so that Windows `.theme` files can be applied.

The project should feel predictable, lightweight, familiar and cohesive.

---

## Why this architecture

An earlier direction (Rust, a custom Smithay compositor, GTK4 shell UI) stalled. The lessons that shaped this version:

1. **The compositor is not the product.** Writing a compositor (DRM, input, focus, XWayland, HiDPI, multi-monitor) is most of the work and none of the distinctiveness. labwc already provides a stacking, Openbox-style compositor with server-side decorations, a window menu, Alt+Tab and keybindings.
2. **GTK4 is the wrong fit for the shell UI.** Its rendering is CSS on a GPU scene graph. Qt Widgets paints with `QPainter` through a `QStyle`, which matches Win95-era drawing directly and needs no CSS.
3. **Client-side decorations are not solvable by the shell.** GTK4 / libadwaita header-bar applications draw their own titlebars regardless of toolkit choice. This is accepted as a limitation, not a problem to fight.

Agents must not reintroduce a custom compositor, GTK shell UI, or a different language without explicit instruction.

## Core Principles

### 1. Simplicity is a feature

Prefer the simplest implementation that satisfies the requirement correctly.

Avoid:

* unnecessary abstraction
* speculative extensibility
* plugin systems
* generic frameworks
* configuration options that have not been explicitly requested
* dependency-heavy solutions to small problems
* separate services where a direct implementation is sufficient

A small amount of duplicated straightforward code is preferable to an elaborate abstraction.

### 2. Integrate, don't reimplement

Before writing a component, check whether an established Linux component already does the job well enough:

* compositor and window management: **labwc**
* window decorations: **labwc themes** (generated by Daytona)
* GTK2/3 application look: **Chicago95** GTK theme, icons and cursors
* file manager, terminal, editor, etc.: existing lightweight applications

Daytona's own code should be the parts that do not exist elsewhere: the NT-style shell UI, the Win95 `QStyle`, the theme converter and the glue that makes them cohesive.

### 3. Do not redesign the project

Agents implement the requested task.

Agents must not independently:

* change the project architecture
* replace major dependencies
* introduce a different UI toolkit
* replace or fork the compositor
* introduce QML / Qt Quick
* introduce new configuration systems
* add extension or plugin architectures
* reinterpret the desktop interaction model
* substantially refactor unrelated code

If a task appears to require an architectural change, stop and explain why. Propose the smallest viable change.

### 4. Preserve the NT interaction model

The desktop follows the Windows 95 / NT 4.0 WIMP interaction model. Unless explicitly instructed otherwise, assume:

* the taskbar starts at the bottom; when unlocked it can be dragged to any edge of its screen, and when locked it cannot be moved or resized (see Taskbar Placement)
* the Start button is on the left
* the notification area and clock are on the right
* the Start menu opens from the Start button towards the centre of the screen (upward when the taskbar is at the bottom) with a vertical banner and cascading submenus
* each normal top-level window has one taskbar button, in launch order
* clicking a taskbar button activates the window; clicking the button of the active window minimises it
* right-clicking a taskbar button shows the window menu (Restore, Move, Size, Minimise, Maximise, Close)
* the Windows key or Ctrl+Esc opens the Start menu (labwc owns global keybindings; its binding runs `daytona-shell --start-menu`, which asks the running shell over D-Bus to open the menu)
* Alt+Tab switches windows; Alt+F4 closes the active window; Alt+Space opens the window menu
* double-clicking a titlebar maximises/restores
* maximised windows occupy the desktop excluding the taskbar
* right-clicking the desktop shows a desktop context menu

Where behaviour is owned by the compositor (titlebars, borders, Alt+Tab, Alt+Space), Daytona achieves it through labwc configuration it ships, not by reimplementing it.

Do not introduce modern alternative behaviours unless explicitly requested, for example:

* tiling
* dynamic workspaces
* global menus
* macOS-style window buttons
* overview-driven workflows
* docks
* automatic taskbar grouping
* gesture-first interaction
* search-first Start menus

## Technology Direction

These are project constraints unless a task explicitly changes them.

* **Language:** C++17 (C++20 features only where the target Qt and compilers support them cleanly)
* **UI toolkit:** Qt 6 Widgets. No QML, no Qt Quick, no style sheets for core styling.
* **Compositor:** labwc (wlroots-based), unmodified upstream where possible. **Approved exception:** NT's raised 3D window frame cannot be drawn by any labwc release (borders are one flat colour), so Daytona builds labwc itself: the `third_party/labwc` submodule, pinned to the version Debian 13 ships, plus the minimal patches in `patches/labwc/`, applied at build time by `scripts/build-labwc.sh` without changing the submodule. The result is installed as `libexec/daytona/labwc` and run by the Daytona session. Keep these patches small, theme-option driven and off by default, and offer them upstream; drop each one once a labwc release Daytona can use includes it.
* **Display protocol:** Wayland, with XWayland provided by labwc for X11 applications
* **Shell surfaces:** `wlr-layer-shell` via LayerShellQt
* **Taskbar window list:** `wlr-foreign-toplevel-management-unstable-v1` (and `ext-foreign-toplevel-list-v1` where it adds value), bound through QtWaylandClient
* **Build system:** CMake
* **Primary architectures:** x86_64 and aarch64
* **Initial packaging target:** Debian `.deb`
* **Minimum platform:** Debian 13 (trixie): Qt 6.8, LayerShellQt 6.3 and the labwc version Debian 13 ships. Do not rely on protocols or labwc features newer than that without explicit approval.
* **D-Bus:** QtDBus (part of Qt) for the notification area, notification balloons and logind. No other D-Bus library.
* **Display/login manager:** external existing implementation
* **Session:** a session file that starts labwc with Daytona's labwc configuration, which autostarts the Daytona shell

The shell is a single process unless isolation gives a concrete benefit. The theme converter is a separate command-line tool because it runs rarely and must work without the shell running.

Daytona is **standalone**. It is not a fork of LXQt, lxqt-panel or any other desktop, and it does not link against their libraries. The goal is the smallest shell that delivers NT shell equivalence; general-purpose desktop code brings configurability and dependencies that Daytona deliberately does not want.

Reading other projects for reference (lxqt-panel, Selkies desktop, Chicago95) is encouraged. Copying small pieces of code requires licence compatibility and attribution.

## Development and Test Environment

A dev container (`.devcontainer/`) based on Debian 13 lets the session run in GitHub Codespaces or locally, without a GPU or physical display:

* labwc runs with the wlroots headless backend and the pixman software renderer (`WLR_BACKENDS=headless`, `WLR_RENDERER=pixman`).
* wayvnc exports the headless output, and noVNC serves it on a forwarded port, so the desktop can be used from a browser.
* `grim` takes screenshots of the headless output for automated smoke tests.

This combination (headless labwc, pixman, a Qt 6 Wayland client with labwc server-side decorations, grim, wayvnc and noVNC) has been run successfully in a plain Linux container. Codespaces itself has not yet been verified.

CI (GitHub Actions) builds Daytona, runs the Qt Test suites and runs a headless session smoke test on every pull request to `main`.

## Compatibility Philosophy

Daytona runs ordinary Linux software. Applications are never required to know about Daytona.

Expected visual results by application type:

| Application type | Frame | Contents |
|---|---|---|
| Qt 5/6 Widgets | labwc server-side, Daytona theme | Daytona Win95 `QStyle` (Qt 6) or nearest equivalent (Qt 5) |
| GTK2 / GTK3 without header bars | labwc server-side | Chicago95 GTK theme with Daytona colours |
| X11 via XWayland | labwc server-side | whatever the application's toolkit provides |
| GTK4 / libadwaita / header-bar apps | client-side, application's own | application's own; **out of scope** |

Do not attempt brittle or application-specific methods to strip client-side decorations or to restyle libadwaita. Compatibility is preferable to visual purity.

Implement standard Wayland protocols rather than application-specific behaviour. Application-specific workarounds require strong justification and a comment explaining when they can be removed.

## Visual Design

The UI should match Windows 95 / NT 4.0 closely in structure and feel. Pixel-perfect emulation is not required, and Microsoft artwork, icons, fonts and trademarks must not be copied or shipped.

Characteristics:

* rectangular bevelled 3D borders (raised and sunken)
* solid colours, no gradients except where a `.theme` explicitly specifies an NT-style titlebar gradient
* conventional titlebars, menus and dialogs
* simple pressed / unpressed button states
* dotted focus rectangles
* compact, mouse-and-keyboard information density
* no animation by default

Do not introduce:

* rounded corners
* translucency or blur
* drop shadows
* large touch-first controls
* floating panels
* oversized whitespace
* transitions

All shell drawing goes through the Win95 `QStyle` and the current `QPalette`, so a theme change restyles the shell without code changes. Do not hard-code colours in widgets.

---

## The Win95 QStyle

The style is a Qt 6 style plugin (subclass of `QCommonStyle`, or `QProxyStyle` over the built-in Windows style if that proves simpler and remains correct).

* It draws with `QPainter` primitives only. No images for basic controls, no style sheets.
* It takes all colours from `QPalette`. The theme converter is responsible for producing the palette.
* It must be usable by third-party Qt 6 applications via `QT_STYLE_OVERRIDE` or qt6ct, not just the shell.
* Bevel widths and metrics must scale with device pixel ratio.

---

## Theme Compatibility

Daytona supports Windows 95 / Plus! era `.theme` files as its colour and appearance format.

The theme tool:

1. Parses a `.theme` file (INI format) as untrusted input.
2. Extracts colours (`[Control Panel\Colors]`), wallpaper, fonts and, where present, cursors, icons and sounds.
3. Generates:
   * a labwc theme (`themerc` and button images) for window frames
   * a Qt palette / colour scheme consumed by the shell and the `QStyle`
   * a GTK3 colour override for the Chicago95 theme
   * wallpaper and cursor settings for the session
4. Writes into the user's data directories only, never system directories.

Rules:

* Missing keys fall back to the Windows Standard scheme.
* Unknown keys are ignored, not errors.
* Paths inside `.theme` files are Windows paths; map them relative to the theme file and never follow them outside the theme's own directory.
* Unsupported elements (e.g. screensavers, sounds if no sound support exists) are reported, not silently dropped.
* Chicago95 Plus! is prior art; reuse its knowledge where licences allow.

Daytona's own settings are a small, documented INI file, not CSS and not a generic theme engine.

## Configuration Policy

Daytona is deliberately not customisable beyond NT shell equivalence.

The rule: **if Windows NT 4.0's shell did not offer it, Daytona does not offer it.** Having an NT equivalent makes a setting eligible, not required; it is only added when explicitly requested.

**Approved exceptions** (post-NT features deliberately included):

* **Lock the taskbar** (Windows XP). It makes the NT-era drag-to-edge behaviour safe to leave enabled.
* **Notification balloons** (Windows 2000). Linux applications send desktop notifications and expect them to be shown; balloons are the closest era-appropriate presentation.
* **Large Fonts is 150%**, not NT's 125% (120 DPI). 150% is the more useful size on today's high-density screens; 125% remains available under Custom....

No other post-NT features are accepted without explicit approval.

Accepted configuration, Display Properties equivalents:

* colour scheme and fonts (normally applied via `.theme` files)
* wallpaper
* clock format (follows the system locale)
* high-contrast schemes and font size, as accessibility options. Font size is NT's Settings tab choice (Small Fonts 100%, Large Fonts 150% (see approved exceptions), custom 100-300%), applied as each screen's scale through wlr-output-management and remembered per screen.

Accepted configuration, Taskbar Properties equivalents:

* taskbar edge (set by dragging, not by a setting in a dialog)
* lock the taskbar
* always on top
* auto hide
* show small icons in Start menu
* show clock

Settings are stored with `QSettings` in a single INI file. No other configuration mechanism is used.

Fixed:

* taskbar contents and their order
* Start menu structure
* titlebar button order
* interaction model

Do not add settings that NT did not have, such as taskbar transparency, alternative Start menu layouts, panel applets or custom widgets. Do not expose a setting simply because it is easy to implement.

## Start Menu

Top to bottom, matching NT 4.0:

* **Programs**: cascading submenus built from `.desktop` files, grouped by freedesktop main categories, alphabetical within each. Entries with `NoDisplay=true`, `Hidden=true`, or `OnlyShowIn`/`NotShowIn` excluding Daytona are omitted.
* **Documents**: the 15 most recent items from `~/.local/share/recently-used.xbel`.
* **Settings**: Control Panel (launches a command set in Daytona's INI file; greyed out if unset), Taskbar... (Taskbar Properties), Display... (Display Properties, colours/wallpaper/`.theme`).
* **Find**: launches a file-search command set in Daytona's INI file; greyed out if unset.
* **Run...**: Daytona's Run dialog.
* separator
* **Shut Down...**: NT-style dialog offering Shut down, Restart and Close all programs and log on as a different user, using systemd-logind over QtDBus. Options logind reports as unavailable are disabled.

NT's **Help** item is omitted; there is no system-wide help viewer to open.

---

## Taskbar Window Menu

Right-clicking a taskbar button shows Restore, Move, Size, Minimise, Maximise, separator, Close (Alt+F4), drawn by the shell with the Win95 `QStyle`.

* Restore, Minimise, Maximise and Close use foreign-toplevel requests. Items that do not apply to the window's current state are disabled, as in NT.
* **Move and Size are always shown disabled.** foreign-toplevel has no request to start an interactive move or resize. They remain available from the titlebar window menu (Alt+Space), which labwc draws. Adding the capability is an upstream labwc/protocol matter, not something to work around in the shell.

---

## Notification Balloons

The shell implements the `org.freedesktop.Notifications` D-Bus service.

* Each notification appears as a Windows 2000-style balloon pointing at the notification area: yellow tooltip background (`QPalette::ToolTipBase`), bold title, body text, optional icon, close button.
* One balloon at a time; further notifications queue.
* A balloon closes on click, on its close button, or after its timeout (application timeout, else 10 seconds). Clicking the body invokes the `default` action if present.
* Supported capabilities: `body`, `actions` (default action only), `icon-static`. Markup, sounds and persistence are not supported.
* No notification history, do-not-disturb or notification centre: none existed in the era.

---

## Desktop

The desktop is a background layer-shell surface on each output showing the wallpaper or desktop colour, plus a right-click menu containing **Properties**, which opens Display Properties. NT's other desktop menu items (Arrange Icons, Line up Icons, Paste, Paste Shortcut, New) act on desktop icons and are omitted while icons are out of scope.

**Desktop icons are out of scope** until explicitly approved. Do not draw files from `~/Desktop`.

## Taskbar Placement

The taskbar behaves like the Windows taskbar:

* By default it is docked to the bottom edge and **locked**.
* "Lock the taskbar" is a checkable item in the taskbar's right-click menu and in Taskbar Properties.
* While unlocked, the user presses on an empty area of the taskbar and drags. The taskbar snaps to the screen edge nearest the pointer (bottom, top, left or right) and stays there on release. There is no free-floating position.
* While unlocked, the user can drag the taskbar's inner edge to change its thickness in whole rows (horizontal) or to a wider width (vertical), as in NT. It cannot be made thinner than one row.
* While locked, dragging and resizing do nothing.
* Edge and thickness persist across sessions.
* On a vertical edge, contents stack vertically: Start button at the top, window buttons below, notification area and clock at the bottom.

Implementation constraints (no new dependencies):

* Placement uses only `wlr-layer-shell` through LayerShellQt: anchors select the edge, the exclusive zone reserves space so labwc keeps maximised windows clear of the taskbar, and the surface size sets thickness. Changing edge means updating anchors, exclusive zone and size, then re-laying out the widgets.
* Dragging relies on the standard Wayland implicit pointer grab: after a button press on the taskbar, motion events keep arriving at the taskbar surface even outside its bounds. The nearest edge is computed from that position and the output geometry Qt reports. Verify this behaviour in labwc before building on it; if it does not hold, stop and report rather than adding a workaround.
* Layout direction is switched with standard Qt layouts (`QBoxLayout::setDirection`), not separate horizontal and vertical widget trees.
* "Always on top" maps to the layer-shell `top` layer, otherwise `bottom`. "Auto hide" sets the exclusive zone to zero and shrinks the surface to a thin strip that expands on pointer entry.
* The taskbar stays on its own output. Moving it between monitors is out of scope until multi-monitor work begins.

## Performance Philosophy

Daytona targets ordinary and low-end systems, in the spirit of the original NT shell. Small is a goal in its own right: binary size, resident memory, dependency count and lines of code should all stay as low as correctness allows.

* The shell should idle at near-zero CPU. No polling and no permanently running timers (the clock timer fires once per minute, aligned to the minute).
* Avoid loading Qt modules the shell does not need (no Qt Quick, no WebEngine, no Multimedia).
* Prefer one process.
* Cache `.desktop` file parsing; refresh on filesystem change notification, not by rescanning on a timer.
* Do not perform filesystem scanning, icon decoding or process waiting on the UI thread when it can block noticeably.

Correctness comes before premature optimisation. Performance claims must be measured.

---

## HiDPI and Multi-Monitor

* Never assume logical pixels equal physical pixels. Use Qt's device-independent pixels and device pixel ratio throughout, including in the `QStyle`.
* Bevels and 1-pixel lines must stay crisp at integer scales and acceptable at fractional scales.
* Do not assume a single output. The taskbar is placed on the primary output initially; the design must not prevent a taskbar per output later.

## C++ and Qt Guidelines

Prefer clear, conventional modern C++ and idiomatic Qt.

Prefer:

* Qt parent-child ownership for widgets; `std::unique_ptr` for non-QObject ownership
* signals and slots for UI events
* `enum class` for meaningful states
* small focused classes and files
* descriptive names
* `const` correctness

Avoid unless justified:

* raw `new` / `delete` outside Qt parent ownership
* deep inheritance hierarchies
* template metaprogramming
* macros beyond those Qt requires
* exceptions crossing Qt event boundaries
* `QWidget::setStyleSheet` for core styling

Compile with warnings enabled (`-Wall -Wextra`) and treat new warnings as defects. Format with clang-format using the repository's configuration.

## Error Handling and Logging

* A failure in one shell component must not take down the whole shell.
* If a Wayland protocol the shell relies on is missing, log a clear warning and degrade (e.g. taskbar without window buttons) rather than crash.
* Use `QLoggingCategory` with per-component categories (`daytona.taskbar`, `daytona.startmenu`, etc.).
* Do not leave temporary debug output in committed code.
* Never show internal error messages or stack traces in user-facing dialogs.

---

## Window State

The compositor is the source of truth for window state.

The taskbar reflects state reported through foreign-toplevel (title, app id, activated, minimised, maximised) and requests changes through the same protocol. It never tracks its own contradictory copy of window state.

---

## Security Boundaries

Treat application metadata, `.desktop` files and `.theme` files as untrusted input.

* Window titles and app ids are not safe for shell execution or file paths.
* Launch applications with `QProcess::startDetached` and structured arguments, following the Desktop Entry `Exec` field-code rules. Do not use `/bin/sh -c` unless shell semantics are explicitly required (e.g. the Run dialog, where the user is typing a command).
* The Run dialog runs as the user; it is not a privilege boundary.
* The session runs as the normal user. No setuid, no root helpers.

---

## Accessibility

* Every shell function is reachable by keyboard (Start menu navigation, taskbar focus, Run dialog).
* Focus is always visible (dotted focus rectangle).
* Set accessible names on shell widgets.
* Colour is never the only indicator of state.
* High-contrast `.theme` files must render correctly.

---

## Testing Expectations

Prefer automated tests (Qt Test) for:

* `.theme` parsing and colour conversion
* labwc theme / Qt palette / GTK output generation
* `.desktop` parsing and Start menu category building
* `Exec` field-code expansion
* taskbar ordering and state transitions given toplevel events
* geometry and scaling calculations in the style

Keep Wayland-dependent code thin so the logic beneath it is testable without a compositor.

Graphical changes should, where practical, extend the headless smoke test (start the session headless, launch the shell, take a `grim` screenshot and check something concrete, such as the taskbar's reserved area or a pixel colour at a known position). Avoid brittle whole-image comparisons.

For graphical changes, also provide a concise manual checklist (the Codespaces noVNC session is suitable), for example:

* launch labwc with the Daytona session and two applications
* click each taskbar button; click the active one to minimise
* right-click a taskbar button and use each window menu item
* open the Start menu with the mouse, the Windows key and Ctrl+Esc; navigate it with arrow keys
* apply two different `.theme` files and confirm shell, frames and a Qt app all change
* unlock the taskbar, drag it to each edge, maximise a window each time and confirm the window clears the taskbar; lock it and confirm it no longer moves
* test at 1× and 2× scale

## Never Fake Success

Do not claim:

* code compiles when it was not compiled
* tests pass when they were not run
* a feature works when it was not exercised
* protocol behaviour that has not been verified
* performance improvements that were not measured

If the environment prevents verification (for example, no Wayland session is available), say so. Partial verification is acceptable; false confidence is not.

## Do Not Guess External Behaviour

Wayland protocols, labwc, Qt, LayerShellQt and the `.theme` format all have subtle behaviour.

* Consult current documentation and protocol XML.
* Check the version actually targeted.
* Do not invent API methods or configuration keys.
* Distinguish between protocol requirement, library behaviour, labwc behaviour, Windows behaviour and Daytona policy.

## AI Task Discipline

Work in small, reviewable units that change one coherent area of behaviour.

Before coding: read the relevant code, identify the smallest set of files to change, understand existing interfaces, and check for related tests.

While coding: keep changes narrow, avoid opportunistic refactors and cosmetic churn, and do not add speculative features.

After coding:

1. Run clang-format.
2. Build with warnings enabled.
3. Run the tests.
4. Summarise exactly what changed.
5. List limitations and anything unverified.

Comments explain why, not what. Compatibility workarounds must say when they can be removed.

Each commit should build and be understandable on its own. Do not mix features, refactors, dependency changes and formatting in one change.

## Decision Rule

When several reasonable implementations exist, prefer the one that is:

1. correct
2. standards-compliant
3. already provided by an existing component
4. easy to understand and review
5. lightweight
6. easy to test
7. boring

A desktop shell is infrastructure. Users should notice their applications, not the shell.
